# explainer-html

## 芯となる考え方

読み手が、資料の内容を自分で確かめて、なるべく早く腹落ちできるようにする。

資料は「結論を信じてもらうもの」ではない。「読み手が自分で裏取りや詳細確認をするための最短ルート」として作る。
そのため、書いた内容には必ず情報元を示す。読み手が1クリック、または1回の検索でたどり着ける形にする。

以下の方針は、すべてこの考え方を具体化したものである。迷ったら「読み手が自分で確かめる時間が短くなるか」で判断する。

## 他の Skill との関係

- この Skill は土台の考え方を持つ。情報元の示し方、事実と推測の書き分け、更新の仕方、目次・印・図の要件
- 固有の Skill（例: review-aid）は、それぞれ固有の構成を持つ。章立て、データ形式、生成手順、図の方式
- 固有の Skill を使うときも、この Skill の方針を満たすようにする。両者が衝突したら固有の Skill を優先する
  - 例: review-aid は図に Mermaid を使う。この Skill の「inline SVG で描く」より review-aid の方式を優先する

## 基本方針

### 1. サイドバーに目次を常に表示する

- PC 幅では左側に固定し、スクロールに追従させる。今読んでいる章をハイライトする
- スマホ幅では折りたたみ式にする
- `assets/template.html` は、本文の `h2[id]` / `h3[id]` から目次を自動で作る

### 2. 図解を多めにして、短時間で理解できるようにする

- 次のものは文章より先に図にする
  - 処理やデータの流れ
  - 要素どうしの関係（例: テーブルの参照関係）
  - 時系列のやり取り（シーケンス）
  - 包含・入れ子の構造（例: 設定の優先順位、ラッパーと中身）
- 図は inline SVG で描き、ライト／ダークの両テーマで読めるようにする。色は直接書かず、テンプレートのトークンを使う
- 描き方は `references/diagrams.md`

### 3. 章や項目ごとに読み手が印を付けられるようにし、サイドバーに進捗として表示する

- 解説の章は「読んだ」「理解した」、TODO や確認事項は「実施済み」「回答済み」
- 状態は localStorage に保存する。try/catch で囲み、保存できない環境でも表示は壊れないようにする
- サイドバーの目次項目に印の状態を出し、全体の進捗（例: 5/12）も出す
- テンプレートでは見出しに `data-mark="chapter"` か `data-mark="todo"` を付けるだけでよい
- 保存キーは `<meta name="doc-id">` で資料ごとに分ける。再公開しても同じ値を保ち、読み手の印を消さない

### 4. 仕様はコードとセットで説明する

読み手が自分でコードを見て確かめられるようにする。

- `ファイルパス:行番号` を付ける。どのコミット（ブランチ／ハッシュ）時点の行番号かを冒頭に書く
- コード片は要点だけに絞る。注目する行をハイライトし、短いコメントを添える
- 冗長になる場合は、コード片を省いてパスと行番号だけにする

### 5. セッション中のやり取りを常に HTML に反映する

- 質問に答えたら、答えをチャットに書くだけで終わらせない。該当する章を更新する
- ローカルなら同じファイルを更新する。Artifact なら同じパスで再公開し、URL を変えない
- 冒頭の「最終更新」を更新する。大きく書き換えた章は、何が変わったかを章の先頭に1行で書く

### 6. 前提知識の章を設ける

- 読み手が用語や概念を「なんとなく」しか知らない前提で、本題の前に基礎から整理する
- 用語の定義、どの単位で管理されているか（例: アカウント単位、キャンペーン単位）、似た概念どうしの違いを押さえる
- 似た概念が複数あるときは、違いを比較表にする

### 7. 確認事項や依頼文は、その項目だけ読んでも分かるように書く

- 「経緯」「関係する仕組み」「今の状態」「確認したいこと」をセットにする
  - 関係する仕組みの例: 設定フラグなら、それが何を切り替えるものか
- 相手にチャットなどでそのまま貼れる文面にする。テンプレートの確認事項カードにはコピーボタンがある
- 宛先（誰に聞くか）を書く

### 8. 情報元は、読み手がすぐたどれる粒度で示す

- 主張ごとに、その根拠の場所を添える。根拠は、コード、チャット、チケット、Wiki、DB の実データ、ライブラリの中身など
- チャットのスレッドなら、親投稿ではなく該当する返信へのリンクにする。重要な発言は原文を引用する
- 日時・場所（チャンネル等）・発言者を併記する
- 資料末尾に参照一覧を置き、本文中の番号（[1], [1-1] など）から飛べるようにする
- DB の実データなら、実行したクエリや見たテーブルを書き、読み手が再実行できるようにする
- 書き方の例は `references/components.md` の「出典」

### 9. 事実と推測を書き分ける

- コードから推定しただけのこと、実際に動かして確認していないことは、そう明記する
- DB などで実データを確認した場合は、確認日と、どこを見たかを書く
- 「仕様上はこうなっているが、実データでは使われていない」のような実態とのずれは、判断に効くので目立たせる
- テンプレートのラベル: `確認済み`（実データや実行で確かめた）/ `未検証`（コードから読んだが動かしていない）/ `推測`（根拠が間接的）

### 10. 読み手が HTML を直接編集した場合は、その変更を取り込んでから更新する

読み手の変更を上書きしない。

- ローカルなら、更新前にファイルを読み直して手動の変更を確認する
- Artifact なら、再公開の前に最新版を読み、変更（タイトルなど）を手元のファイルに取り込む
- 取り込んだ変更があれば、報告のときに一言触れる

### 11. 文体は常体。1文を短くし、回りくどい言い方を避ける

## 手順

### 1. 出力先を決める

- 指示が無ければ手元の HTML ファイル。既定のパスは `~/explainer-html/<topic>.html`
- 「artifact にして」などの指示があれば Artifact として公開する。公開手段が無い環境では手元に作り、その旨を伝える
- 手元に作ったものを後から Artifact にする場合も、同じファイルを元にする

### 2. 材料を集め、情報元をその場で控える

- 調べながら、根拠ごとに URL・日時・場所・発言者・コミットを控える。後から探し直すと粒度が粗くなる
- コードを読むときは、基準のブランチとコミットハッシュを最初に確定する（`git rev-parse --short HEAD`）
- 実データを見たら、クエリと実行日と接続先を控える

### 3. 章立てを決める

既定は次の順。該当しない章は省く。固有の Skill があればその構成に従う。

1. 要約（結論を3行以内。各文に出典）
2. 前提知識（用語・管理単位・似た概念の比較表）
3. 本題（図 → 要点 → コード片の順）
4. 実態とのずれ、未確認の点
5. 確認事項・TODO
6. 参照一覧

### 4. テンプレートを複製して中身を書く

- `assets/template.html` を出力先にコピーし、`TITLE`・`TOPIC`・`REPO`・`BRANCH @ HASH` などを置き換える
- サンプルの章は消して、自分の章に置き換える。部品の使い方は `references/components.md`
- Artifact として公開する場合は、先に `artifact-design` と `artifact-diagramming` の Skill を読む。
  テンプレートは外部スクリプトに依存しない1ファイルなので、そのまま公開できる

### 5. 確かめてから渡す

- 可能ならヘッドレスブラウザで一度開き、描画の崩れ（図のはみ出し、目次の欠け）が無いか見る
- 本文の `[n]` がすべて参照一覧に存在するか確かめる

### 6. 報告する

パスまたは URL、章の構成、`推測` や `未検証` のまま残っている点、確認事項の件数を短く伝える。

### 7. 以降のやり取りで更新し続ける

質問・追加調査・訂正のたびに、次の順で行う。

1. 手動の変更を確認する（ローカルは読み直す。Artifact は最新版を読む）
2. 該当する章を更新する。新しい根拠は参照一覧に足す。訂正した主張は、古い記述を消して正しい記述と根拠に置き換える
3. 同じパス／同じ URL に反映する
4. チャットには、答えの要点と、どの章を更新したかを書く

## 発動フレーズの例

- 「解説 HTML を作って」「この仕様を HTML で解説して」
- 「調べた内容を HTML にまとめて」「この調査を資料にして」
- 「前提知識を HTML で整理して」「見積もり前に調べたことを HTML にして」
- 「確認事項を HTML にまとめて」「質問リストを HTML にして」
- 「artifact にして」「さっきの資料を Artifact で公開して」
