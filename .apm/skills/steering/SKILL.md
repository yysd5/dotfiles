# Steering スキル

開発案件の要件・設計・タスクリストを`.steering/`配下に
ファイルとして残し、それに沿って実装を進めるためのスキル。

ファイルに残す目的は2つある。

- 会話の圧縮やセッション切り替え、別ツールへの移行を
  越えて作業を再開できるようにする
- ユーザが計画と進捗をレビューできる場所にする

そのため、tasklist.mdは常に実態と一致させておくこと。
ユーザが開いたときに今どこまで進んでいるか分かる状態が
このスキルのゴールである。

## ファイル構成

```
.steering/[YYYYMMDD]-[機能名]/
├── requirements.md
├── design.md
└── tasklist.md
```

テンプレートはこのSKILL.mdと同じディレクトリの`assets/`配下にある。

## モード1: ステアリングファイル作成

1. `.steering/[YYYYMMDD]-[機能名]/`を作成し、
   テンプレートを元に3ファイルを作る
2. 機能のideasディレクトリ（`.docs`配下など）のメモを
   読み、requirements.mdとdesign.mdを書く
   - メモは完全な仕様ではない。不明点、決めるべき点、
     テストや検証の実行コマンドなどが曖昧なら、
     ユーザに確認しながら実装可能な状態まで詰める
3. requirements.mdとdesign.mdを元にtasklist.mdを書き、
   これもユーザと対話して仕上げる
   - タスクの単位は1つの意思決定単位とする
     （クラスやメソッド単位で機械的に分けない）
   - 実装タスクは`/tdd-workflow`のTDDプロセスを意識する
   - 計画段階で実装可能なタスクのみを載せる

## モード2: 実装

tasklist.mdの順に1タスクずつ進める。

- 着手時に`[ ]`→`[-]`にする
- 実装が終わったらユーザに確認を依頼し、
  承認を得てから`[-]`→`[x]`にする。
  コミットはユーザ自身が行うので、
  その際にコミットメッセージを提案する
- 進捗はまとめてではなく、その都度tasklist.mdに反映する

計画は実装中に変わってよい。変わったら黙って進めず、
tasklist.md（必要ならrequirements.md, design.md）を
実態に合わせて更新する。

- タスクが大きすぎる: サブタスクに分割して追記する
- 技術的理由で不要になった: 理由を添えて取り消し線にする
  - 例: `- [x] ~~タスク名~~（不要: XをYに置き換えたため）`
- 計画自体に問題がありそう: 進めずにユーザに相談する

「時間がかかる」「難しい」といった理由で
タスクを勝手に先送りしたり、未完了のまま終えたりしないこと。
後回しにしたい場合はその判断自体をユーザに委ねる。

## モード3: 振り返り

全タスクの完了後、tasklist.mdの「実装後の振り返り」に
以下を記録し、ユーザに確認を依頼する。

- 実装完了日
- 計画と実績の差分（変更点とその理由）
- 学んだこと
- 次回への改善提案
