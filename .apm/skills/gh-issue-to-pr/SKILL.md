# 実装済みタスクのIssue化とPR作成ワークフロー

手元にある実装済みの変更を整理し、GitHub CLI (`gh`) を使って
Issue作成、ブランチ整理、論理的な粒度でのコミット、PR作成までを
対話的に進める。

## 前提

- すでに機能の実装や修正が手元（現在のブランチ）で行われていること
- `git status` や `git diff` で変更内容が確認できること

## ワークフロー

### ステップ1: 変更内容の確認とIssue作成

1. 現在の変更内容 (`git diff` および `git diff --cached`) を分析し、
   どのような修正が行われたか把握する
2. 修正内容に基づき、Issueの `title` と `body` を提案する
3. ユーザに提案内容の確認とIssue作成の許可を求める
4. 許可が得られたら `gh issue create` を実行し、Issue番号を取得する

### ステップ2: 専用ブランチの作成と移動

1. Issue番号に基づいたブランチ名を提案する（例: `issue/123-feature-name`）
2. ユーザにブランチ作成と移動の許可を求める
3. 許可が得られたら、現在の変更を保持したまま
   `git checkout -b [ブランチ名]` で新ブランチを作成して移動する

### ステップ3: 論理的な粒度での分割コミット

変更を一括ではなく、意味のある単位（feat, fix, refactor等）に分けてコミットする。

1. 変更をどう分割してコミットするか（メッセージ案と対象ファイル）を提示する
2. 各コミットについて、`git-committer` スキルのガイドラインに沿って
   メッセージを確定し、ユーザの確認を得てからコミットする
3. 全ての変更がコミットされるまで繰り返す

### ステップ4: PushとPRの作成

1. エージェントの環境からはpushできないため、
   ユーザに `git push -u origin [ブランチ名]` の実行を依頼する
2. push完了の連絡を受けたら、PRのタイトルと本文
   （`Closes #[番号]` を含む）を提案する
3. ユーザの許可を得て `gh pr create` を実行し、PRのURLを提示する

コミット、push依頼、PR作成は1つのコマンドにまとめず、段階ごとに実行する。
マージはユーザが行う。

## 注意事項

- 競合や操作の失敗が起きた場合は、無理に継続せずユーザに状況を報告する
