# テスト駆動開発 (TDD) ワークフロー

TDDの進め方（Red-Green-Refactor）を定める。言語を問わず進め方は同じ。

- 何をどうテストするか（観点、振る舞いの検証、モック方針等）は
  `test-design` を参照
- 言語ごとの書き方や実行コマンドは各言語スキル（例: `java-dev`）を参照

## 基本の流れ

1. **Red**: 実装の前に、期待する振る舞いを表すテストを書く。
   対象のテストだけを実行し、想定どおりの理由で失敗することを確かめる。
   失敗を見ないと、そのテストが正しく検証できているか分からないため
2. **Green**: テストを通すための最小限のコードを書き、
   対象のテストが通ることを確かめる
3. **Refactor**: テストが通る状態を保ったまま、コードを整える

テストの実行は、全体ではなく対象のテストクラスやメソッド単位で行う。
全体の実行は区切りのよいところでまとめて行う。

## 作業の種類ごとの進め方

### 新機能

上記の流れで、振る舞いを1つずつ追加していく。

### バグ修正

修正の前に、バグを再現するテストを書いて失敗することを確かめる。
そのうえで修正し、テストが通ることを確かめる。
再現テストは回帰防止としてそのまま残す。

### リファクタリング

振る舞いは変えないので、新しく失敗するテストは書かない。
既存のテストが通る状態を保ったまま進める。
対象の振る舞いを守るテストが足りなければ、先にそれを補ってから着手する。
