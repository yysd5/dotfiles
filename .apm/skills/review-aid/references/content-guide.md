# 構成ルール

レビュアーが「前提をそろえる」「確認を終えてよいと判断する」までの時間を短くすることが目的。
どの節も「読む人が次に何を知りたくなるか」の順に並べる。

## 目次

- 前提知識タブ
- レビュー本編タブ
- 図と絵の使い分け
- 文章

## 前提知識タブ

節の並びは次のとおり。該当しない節は省く。

1. **用語集**（`glossary` ブロック）
   - このページとレビュー本編に説明なしで出てくる用語を、分類ごとにまとめる
   - 裏付けが取れない説明は書かない。推測で書いた語は、報告のときにユーザーに伝える
2. **対象概念の概要**（例: 「〇〇とは」。今回の変更が扱う中心の概念）
   - 何を表すものか、どう作られるか（生成パイプラインの図）、既存ではどこでどう使われているか（表）
   - 社内ドキュメントに大体あるので、プロファイルに書かれた手段で探す。出典のリンクを付ける
3. **仕様の要点**: カード数枚と、利用範囲などの表
4. **データの流れ**: データソース → システム内のクラス → 出力先 の全体図（Mermaid の flowchart）。システム内のクラスは必ずシステムの枠の中に置く
5. **処理の順番**: 以降の節の番号（A-1, B-1 …）で描いた全体図
6. **A. データロード**（別スレッドや定期ロードがある場合）: 起動時と定期ロードの仕組み → 各マスタの読み込み、を処理順に
7. **B. リクエスト処理**: 変更前のシーケンス図 → 処理順に B-1, B-2 …
8. **補足**: 仕様上のケース分け（`simulator` ブロック）、セルフチェック（`quiz`）

### コード片の節（A-*, B-*）の中身

1. 見出しの直後に `purpose`（目的 / 入力 → 出力 / 今回との関係）
2. コード片（`code` ブロック）。**変更前（base）** のコード。行頭 `!` で重要な行をハイライト。長いものは `...` で省く
3. データの絵（`html` ブロック）。下の「図と絵の使い分け」を参照
4. 「押さえておくこと」（`point` ブロック）: レビューで効いてくる事実だけ
5. 「レビュー本編タブでは」（`later` ブロック）: 本編の該当の変更へのリンク

処理概要はコードを読まなくても分かる言葉で書く。「マスタと突き合わせる」だけでは何のことか分からないので、何を何に変える処理で、なぜ要るのかを書く。

## レビュー本編タブ

データの `review` に入れる。並びはテンプレートが決める。

1. **サマリ**: 3つの仕分けの件数（自動）、テスト結果、時間の使い方（重点の変更、読まなくてよいファイル）
2. **PR の目的（4つの問い）**: SKILL.md 参照。出典必須
3. **影響範囲の全数確認**: 変わる値・メソッドごとに、利用箇所を全件（件数と path:line）と、影響の有無の理由。前提条件（「この時点では未設定」など）も行にする
4. **変更後の図**: シーケンス図とクラス図。今回の変更箇所を色分けする
   - シーケンス図: 新規は `rect rgba(46,160,67,0.18)`、変更は `rect rgba(212,160,23,0.20)` で囲む
   - クラス図: `style <Class> fill:#2ea04330,stroke:#2ea043,stroke-width:2px`（新規）、`fill:#d4a01733,stroke:#b8860b,stroke-width:2px`（変更）
   - 凡例（`legend`）を付ける
5. **仕様とテストの対応**: 仕様の項目 → 実装した変更 → テスト。テストが無い行は空にする（「テストなし」と出る）
6. **変更ごとのウォークスルー**（`parts`）: データの受け口 → 中核ロジック → 影響の遮断 → 出力 → テスト、のように依存の順に Part を分ける
   - `diff`: 差分から要点だけ。`+` / `-` / 空白 の行頭記号を残す
   - `say`: 作者の意図の**推定**。差分・コードコメント・コミットメッセージ・仕様書から書く。作者本人の説明のように断定しない
   - `look`: 作者が見てほしいと思われる点
   - `ai`: 指摘。`references/triage.md`
   - `focus`: `hot`（重点）/ `normal` / `skim`（流し読み）。レビュアーの時間配分の目安

## 図と絵の使い分け

- **全体の流れ**（データの流れ、処理の順番、シーケンス、クラスの関連、生成パイプライン）: Mermaid
- **個々の処理の説明**: フローチャートではなく、データの中身が見える絵を HTML で描く。テンプレートの CSS クラスを使う
  - RDB: テーブルの行の例（`table.dbt`）。できれば実データ。列名は DDL どおり
  - FileDB・KVS: ファイル構成（`.box`）、キー → 値の表（`table.dbt`）、1レコードを展開した中身（`.rec`、`.rk` がキー、`.rf` がフィールド）
  - メモリ上の構造（Map など）: `.rec` を並べる
  - 変換処理: 変換前 → 変換後をチップ（`.chips` と `.chip`、`.chip.keep` / `.drop` / `.anc` / `.mark`）と矢印（`.arr`）で
  - 時間の流れ（定期ロードなど）: `.tl` のタイムライン
  - 判定（条件に合うか）: 入力の集合と候補の表に、判定（`.verd.ok` / `.verd.ng`）を並べる
  - 外枠は `div.ill`、横並びは `div.row`、縦並びは `div.col`、見出しは `.ttl`、注記は `p.note`
- 文字だけで足りる節（単純な値の受け渡しなど）には絵を付けない
- 絵の中の値は、実データか「例」かを注記で分かるようにする

## 文章

- 常体。短い文。主語と目的語をはっきり書く
- 装飾的な言い回し（「〜ではなく〜」の対比の多用、括弧での言い換えの連発）を避ける
- 用語は用語集に載せたものに揃える
- HTML を文字列に入れるときは `<code>` などのタグをそのまま使える。`<` をテキストとして出すときは `&lt;`
