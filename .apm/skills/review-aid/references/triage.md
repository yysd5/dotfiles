# AI レビューのトリアージ

レビューの主な成果物は「指摘」よりも「確認を終えてよい根拠」。問題が無かった点も根拠付きで残し、
レビュアーが同じ確認を繰り返さずに済むようにする。

## 3つの仕分けとレベル

| 仕分け | lv | 表示 | PR コメントのタグ | 必須のフィールド |
| --- | --- | --- | --- | --- |
| 人間の判断が要るもの | `must` | 修正必須 | `[must]` | `why` `view` `options` `draft` |
| 同上 | `sug` | 要議論 | `[imho]` | `why` `view` `options` `draft` |
| 同上 | `minor` | 軽微 | `[nits]` | `why` `view` `options` `draft` |
| 要確認 | `check` | 要確認 | `[ask]` | `resolve` `draft` |
| 見なくてよいもの | `ok` | 問題なし | なし | `ev` は R1〜R4 |

- `must`: 仕様違反やバグ。マージ前に直す必要があるもの
- `sug`: 直すかどうか・どう直すかが判断や好みになるもの（設計、テストの追加、DRY など）
- `minor`: 細かい指摘。**明文化された規約（観点 Skill の条文など）を引用できるものだけ**出す。引用できないなら出さない
- `check`: コードからは決められず、人が事実を見れば決着するもの（ドキュメントの更新、外部の状態、依存ライブラリの差分など）。`resolve` に「何を確認すれば決着するか」を書く
- `ok`: 観点に沿って確認し、問題が無かったもの

「人間の判断が要るもの」は多くても数件に絞る。`why`（なぜ人間が判断するのか）、`view`（AI の見解）、`options`（選択肢）を必ず付ける。

## 根拠のレベル（ev）

| ev | 内容 | 「見なくてよい」に入れてよいか |
| --- | --- | --- |
| R1 | テストが実際に通った証跡 | 可（実行したことと、ログの所在を書く） |
| R2 | 全数を確認した | 可（件数と箇所を書く） |
| R3 | 一次資料（仕様書、設計ページ、DDL など）の原文を引用 | 可 |
| R4 | コードの構造から言える | 可（path:line を示す） |
| R5 | 読んでそう思っただけ | **不可**。`check` にして、何を確認すれば決着するかを書く |

- 「テストが無い」という事実は R2 などで確認できるが、それで良いかの判断は人間に残す（`sug` にする）
- ファイル名と行番号を示せない根拠は R5 扱い

## 指摘の書き方

- `short`: ひとことで言うと（30〜60字、日常語）
- `where`: 所在（path:line、または「〜の呼び出し N件」）
- `persp`: 観点（観点 Skill の番号と名前。例 `3-2 重複ロジック`）
- `body`: 事実と理由。常体
- `draft`: PR コメントの雛形。**丁寧な提案調**（「〜ではないでしょうか」「〜いただけますか」）。タグはテンプレートが先頭に付けるので書かない。200字程度まで
- `code` / `codeLang` / `codeNote`: コード修正を提案する指摘には修正案のコード片を付ける。前提や、合わせて直す必要があるテストがあれば `codeNote` に書く。修正案は実行・コンパイルしていないなら、報告でそう伝える

## 影響範囲の全数確認

振る舞いが変わりうる値・メソッド・フィールドごとに、main コードの利用箇所を grep で全件挙げる。
1か所ずつ「影響が無い理由」または「意図どおり変わる理由」を書き終えたら、確認を終えてよい。
処理順などの前提（「この時点では未設定」）も、その前提を崩しうる箇所を全件挙げて確かめる。
