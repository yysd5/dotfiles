# review-aid

レビューで時間がかかるのは、指摘を探すことよりも「仕様と既存コードを理解する」ことと「確認を終えてよいと判断する」こと。
この Skill は、その2つを先回りして用意した1枚の HTML を作る。

- 前提知識タブ: レビューに必要な前提（用語、概念、既存コードの処理の流れ、データの中身）
- レビュー本編タブ: 変更ごとの説明と AI レビュー。指摘だけでなく「見なくてよい理由」も根拠付きで残す

見た目と振る舞いは `assets/template.html` に固定してある。Claude が作るのは中身のデータ（JSON）だけで、
`scripts/build.py` がテンプレートに流し込む。デザインを毎回作り直さないこと。

## 引数

- 比較するブランチ（省略時は `develop`。無ければ `main` / `master`）
- 仕様書の URL（省略時はコミットメッセージ、ブランチ名のチケット番号、PR 本文から探す）
- `--publish`: Claude の Artifact として公開する。指定が無ければ手元の HTML だけを作る
- `--out <path>`: 手元に出す HTML のパス

出力先を聞かれていない場合は、手元の HTML を既定にする。Artifact を公開する手段が無い環境では、`--publish` があっても手元の HTML を作り、その旨を伝える。

## 手順

### 1. プロファイルを選ぶ

プロファイルは、そのプロジェクト固有の設定を書いた Markdown。社内の情報を含みうるので、この Skill 本体（公開リポジトリで管理している）には置かない。次の順に探し、最初に見つかったものを使う。

1. 対象リポジトリの `.review-aid/profile.md`（特定のツールのディレクトリに依存しない置き場所。Git 管理外にしておく）
2. `~/.config/review-aid/profiles/*.md` のうち、frontmatter の `match`（リポジトリ名や remote URL の一部）が対象リポジトリに合うもの

書き方は `profiles/_template.md`。
プロファイルには、そのプロジェクト固有のこと（レビュー観点 Skill、仕様書の置き場所、実データの確認手段、実行モデル、テストの実行方法、生成物のパターン、出力先の上書き）が書いてある。
該当が無ければ汎用の既定値で進め、足りない情報は推測で埋めずにユーザーに聞く。

### 2. 差分と経緯を集める

- `git log <base>..HEAD`、`git diff <base>...HEAD --stat`、生成物を除いた `git diff`
- 仕様書と関連ドキュメント（プロファイルの取得方法に従う）
- 経緯の探索は上限を決めて打ち切る目安にする（ドキュメント8本程度、過去 PR 5本程度）。
  「PR の目的の4つの問い」（下記）が埋まったら終えてよい

### 3. 既存コードを読んで、前提知識タブの骨組みを決める

`references/content-guide.md` の「前提知識タブ」に従う。要点:

- 冒頭に用語集と、対象概念（今回の変更が扱う概念）の概要・既存の使われ方
- データロード（別スレッドや定期ロードなど）がある場合はそれを先に、次にリクエスト処理を、それぞれ処理の順に
- 各節の冒頭に「目的 / 入力→出力 / 今回との関係」
- コード片は変更前（base）のもの。処理の流れ・データの形は絵で見せる（RDB は行の例、FileDB/KVS はキーと値の中身、変換は前後の値）

### 4. 実データを確認する

プロファイルに実データの確認手段（SQL 実行ツールなど）があれば、絵や例に使う値を本番の実データから取る。
取れない値は「例」と明記する。個人情報や秘匿情報は載せない。

### 5. AI レビューを行う

- レビュー観点はプロファイルが指定する Skill（リポジトリのレビュー観点）を読み込んで使う。無ければ一般的な観点（機能要件、デグレ、保守性、性能、テスト、ドキュメント）
- 影響範囲は全数を確認する。変わる値・メソッドの利用箇所を grep で全件挙げ、1か所ずつ理由を書く
- 各指摘に根拠レベル（R1〜R5）と所在（path:line）を付け、3つに仕分ける。基準は `references/triage.md`
- 「作者の意図」は推定であることを明示する。作者本人の説明のように断定しない

### 6. 関連テストを実行する

プロファイルのコマンドで、変更に関係するテストを実行する。結果（件数、失敗、スキップの理由）とログの所在を記録する。
実行できなかった場合はそう書く。「通った」と書けるのは実行して確かめたものだけ。

### 7. データを作って HTML を生成する

データの形式は `references/data-schema.md`。プロファイルに実例データの場所が書いてあれば、それも参考にする（大きいので必要な部分だけ jq などで見る）。

```bash
python3 <skill>/scripts/build.py <data.json> <output.html> [--mode local|artifact]
```

build.py は典型的な誤り（id の重複、R5 の「問題なし」、判断が要る指摘に選択肢が無い など）を検査する。error は直してから再実行し、warning は内容を見て直す。

- 手元: 既定の出力先は `~/review-aid/<リポジトリ名>/<ブランチ名>.html`（プロファイルで上書き可）。データの JSON も同じ場所に `<ブランチ名>.data.json` として残す（後で直すため）
- Artifact: `--mode artifact` で生成し、Artifact を公開する手段で公開する。同じブランチを作り直すときは同じ URL を更新する

生成後、可能ならヘッドレスブラウザなどで一度だけ開いて、描画エラー（Mermaid の構文エラー、空のタブ）が無いか確かめる。

### 8. 報告する

出力先（パスまたは URL）、AI レビューの仕分けの件数、判断が要るものの要約、確認できなかったこと（実行できなかったテスト、見られなかったドキュメント）を短く伝える。

## PR の目的の4つの問い

レビュー本編の冒頭に置く。それぞれ出典を付ける。埋まらない問いは「作者への質問」に変える。

1. この PR は何を達成しようとしているか（1文）
2. なぜ今それが必要か
3. 採用しなかった選択肢とその理由
4. 過去の方針・前例

## ユーザーの好み（このプロファイルに依らない共通ルール）

- 日本語は常体。PR コメントの雛形だけは丁寧な提案調
- PR コメントの雛形の先頭にタグ: `[must]` 修正必須 / `[imho]` 要議論 / `[nits]` 軽微 / `[ask]` 事実の確認
- コード修正を提案する指摘には、修正案のコード片を付ける（雛形にも Markdown のコードブロックで入る）
- `[nits]` は明文化された規約（観点 Skill など）を引用できるものだけ出す
- 行番号は HEAD 時点で、どのコミット時点かをヘッダに書く
