# Jira見積もりエピック作成スキル

## 使うタイミング

- 「〜の見積もり準備」「見積もりチケットを作って」等の指示を受けたとき
- 過去の見積もりエピックのフォーマットに沿った新しい見積もりエピックを
  作りたいとき

## 手順

### 0. プロジェクト知識の読み込み

チーム名の呼び名や確認先など、プロジェクト固有の知識は
Skill 本体ではなく、リポジトリ外のファイルで管理している。

1. 作業ディレクトリで `git remote get-url origin` を実行し、
   URL から `<owner>/<repo>` を取り出す
    - 例: `git@bitbucket.org:foo/bar.git` → `foo/bar`
2. `~/.claude/project-knowledge/<owner>/<repo>.md` があれば読む
    - 無ければこの手順は飛ばす
3. 呼び名・確認先などは、本 Skill の一般的な記述より
   このファイルの記述を優先する

### 1. 調査

1. 元チケット(見積もり依頼元)の内容を確認する
2. 関連する Slack / Confluence などの一次情報を確認する
    - ドキュメントの記述だけで判断せず、必ず一次情報(Slackスレッドなど)
      に当たる。同じ用語が複数の異なる意味で使われているケースがあるため
      注意する
    - 用語の意味に少しでも疑いがあれば、コードベースの検索結果だけで
      結論を出さず、Slack検索等で裏を取る
3. 対象コードベースを調査し、変更が必要になりそうな箇所・
   既存の類似実装パターンを特定する
4. 不確定要素を「確認事項」としてリストアップする
    - 各確認事項には「誰(どのチーム)に確認するか」
      「回答によって対応方針・工数がどう変わるか」を必ずセットで書く
    - 確認先は「誰がその判断を持っているか」で決める。依頼元ではなく、
      技術的な判断ならその技術を持つチームにする
    - 確認先は基本的に個人名よりチーム名(「インフラチーム」等)の方が好まれる
    - 決まっていない方針は断定しない。前提で対応方針が分岐する場合は
      「合意できた場合／できない場合」のように両方のケースを書く
    - 依頼されていない制御を確認事項として増やさない
      (既存の類似機能でもやっていない制御など)
5. 過去の見積もりエピックを Jira で検索し、フォーマットを確認する
   (`searchJiraIssuesUsingJql` 等でプロジェクト内の過去エピックを探す。
   なければユーザーに実例を1つ聞く)

### 2. フォーマット

タイトルは `[リリース版] 〇〇対応` の形にする。
リリース版が決まっていない場合は `[TBD] 〇〇対応` とする。

見積もりエピックの description は以下の構成に従う。

関係者          ← 見出しレベル1。テキストに underline 装飾

背景            ← 見出しレベル1。underline

対応内容 (合計h) ← 見出しレベル1。underline

※ 合計h 切り上げてXh   ← 8h(1人日)単位に切り上げる

実装者 (Xh)     ← 見出しレベル2。underlineなし

キャッチアップ (Xh)  ← 見出しレベル3。underlineなし

仕様 (Xh)       ← 確認事項をここに列挙(上記1節4参照)

DB作業 (Xh)     ← 該当する場合のみ

実装 (Xh)

レビュー者 (Xh)

- キャッチアップ (2〜4h)
- PRレビュー (Xh)
- 内部結合テスト項目レビュー (Xh)
- 内部結合テスト実施レビュー (Xh)

内部結合テスト作成者 (Xh)

- キャッチアップ (2〜4h)
- 作成 (Xh)

内部結合テスト実施者 (Xh)

- キャッチアップ (2〜4h)
- 実施 (Xh)

関連ドキュメント  ← 見出しレベル1。underline

備考            ← 見出しレベル1。underline


「関係者」セクションは具体的な個人名ではなく、大まかな関与区分
(例:「技術内部」「XXチーム」)で書かれることが多い。

各セクションの書き分け:

- 背景には、案件の目的・経緯・現状の事実だけを書く。
  「〜を共有する」「〜は行わない」などの作業や方針、注意点は
  対応内容か備考に置く
- 実装者のキャッチアップには、今回の変更に必要なことだけを書く。
  関連はするが今回触らない箇所の仕組みは書かない
- コード変更が無い案件では「実装」セクションを作らず、
  実配信確認・乖離確認のように実際の作業単位でセクションを切る
- テストの中身への言及(何をテストするか、デグレ確認の範囲など)は
  「内部結合テスト作成者」の欄にまとめる。
  「内部結合テスト実施者」の欄はキャッチアップと実施の工数だけにする
- 内部結合テストのケースは「案」として書く。実際にケースを作るのは
  作成者なので、「ケースの案。最終的な構成は作成者が決める。」のように
  案であることが分かる書き方にする
- 特定の経路(特定の接続先など)だけをテストする場合は、
  なぜその経路なのかの背景を書く
- デグレ確認で足りるものはデグレ確認に留める。
  当時テスト済みの既存機能を改めてテストし直す項目にはしない
- 関連ドキュメントには Jira・Slack・Confluence などの一次情報だけを載せる。
  見積もり前の調査で作った Claude の Artifact(claude.ai/artifact/...)は
  載せない
- チケットは素の URL で書く(Jira 側でスマートリンク表示になる)

### 3. 工数のルール

- 工数の起点は案件の複雑さで段階を分ける。起点の値を機械的に積まない
    - 新規機能や他チームとの調整を伴う案件: 実装者のキャッチアップ 8h を起点とする
    - 既存パターンの踏襲やライブラリのバージョン更新のような定型案件:
      キャッチアップ 2h・仕様 0h を起点とする。
      レビュー者・テスト担当のキャッチアップ行も省いてよい
    - 例: pom 1行の更新 + 内部結合テストの案件では、実装者 3h
      (キャッチアップ 2h / 実装 1h)、レビュー者・作成者・実施者 各2h、
      合計 9h → 切り上げて 16h とした
- 確認事項が実質無い案件では「仕様」セクション自体を置かない
- レビュー者・内部結合テスト担当のキャッチアップは2〜4h程度を目安にする
- 各セクション(仕様、DB作業など)の中の小項目には時間を付けない
- 問題が無ければ発生しない作業(調査バッファなど)は「バッファ」と明記し、
  依頼次第の作業には「（Optional）」と付ける
- 合計工数は8h(1人日)単位に切り上げ、切り上げ前後の値を
  「※ Xh 切り上げてYh」の形で明記する

### 4. 本文の書き方

- 「なぜその作業が必要か」が読み手に分かるよう理由を書く
- 確認できていない事柄を推測で書かない
- 「対応済み」と書くときは、何が対応済みなのかを書く
- ライブラリ内部のクラス名・メソッド名を出すときは、
  それが何のための処理かを書く。必要なら IDE での探し方も書く
    - 例: jar 内のクラスは IntelliJ の Navigate > Symbol で
      「プロジェクト外の項目も含める」をオンにすると探せる
- 社内で使われていない言い回しを作らない。社内で使われている言葉に
  合わせる(例: ピクセルを「鳴らす」ではなく「発火させる」)。
  迷ったら過去のチケットや Slack での使われ方を確認する

### 5. Jira作成時の注意 (ADF)

- `createJiraIssue` を markdown経由 (`contentFormat: "markdown"`) で
  作成すると、見出しレベル1のunderline装飾は再現できない
- underlineを最初から正しく反映したい場合は `contentFormat: "adf"` を使い、
  見出し (`heading`, `level: 1`) の `content` 内テキストノードに
  `marks: [{"type": "underline"}]` を付与してADFを直接組み立てる

  ```json
  {
    "type": "heading",
    "attrs": { "level": 1 },
    "content": [
      { "type": "text", "text": "関係者", "marks": [{ "type": "underline" }] }
    ]
  }
  ```

- 見出しレベル2・3にはunderlineを付けない

### 6. 起票前の確認

- 作成前に必ずドラフトをチャット上でユーザーに提示し、確認を得てから
  `createJiraIssue` を実行する(Jiraへの起票は他者から見える操作のため)
- 「見積もりの内容自体が妥当か(工数感やタスクの過不足)」は
  コードベース調査だけでは判断できないことが多い。ユーザー自身の
  ドメイン知識での最終確認を必ず挟む
- 提示前に、手順0で読んだプロジェクト知識の呼び名・確認先に
  沿っているかを見直す
